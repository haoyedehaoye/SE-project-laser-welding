# 正式代码分层与预测性维护路线

> 本文只描述正式运行代码；`test/` 保留为历史实验与回归参考，不再作为主系统入口。

## 1. 五个正式模块

```text
app/
├── data_collection/   数据收集
│   ├── current.py      STM32 电压/电流协议、串口与模拟采集
│   ├── video.py        海康工业相机的稳定导入边界
│   └── inputs.py       温度矩阵、机械臂速度/时间接入边界
├── data_quality/      数据质量检测
│   └── service.py      时效、有限数值、量程和矩阵结构检测
├── data_analysis/     数据分析
│   ├── xgboost_models.py  全部 XGBoost 模型注册与推理
│   └── maintenance.py     预测性维护数据就绪度
├── frontend/          前端
│   └── index.html      视频、四模态、模型和联合分析页面
└── data_transport/    数据传输
    ├── event_bus.py    有界内存事件总线
    └── pipeline.py     收集 → 质量检测 → 发布的唯一管线
```

`app/api/` 只负责 HTTP/WebSocket 协议，`app/core/` 保留公共数据契约和生命周期。
原 `app/devices/camera/` 与 `app/services/camera_service.py` 暂时作为相机底层实现保留，
由 `data_collection/video.py` 提供稳定边界，避免一次性迁移影响已完成的真实相机联调。

## 2. 四类数据状态

| 数据 | 当前状态 | 正式入口 | 下一步 |
|---|---|---|---|
| 电流（同时保存电压） | 已实现 | STM32 串口或 `POST /api/data/current` | 用真实协议和量程校准 |
| 焊接视频 | 已实现 | 海康 MVS、`/api/camera/stream` | 录像索引、帧特征与工况关联 |
| 温度矩阵 | 接口已建立 | `POST /api/data/temperature` | 接热像仪 SDK，确定矩阵频率和坏点规则 |
| 机械臂速度和时间 | 接口已建立 | `POST /api/data/robot` | 接机器人只读协议并补充轴位置/负载/故障码 |

所有数据统一变成 `DeviceEvent`，包含设备时间、接收时间、单位、真实/模拟标记和有效性。
模拟数据不得与真实生产数据混存。

## 3. XGBoost 模型使用方式

正式分析层会发现并调用当前 `models/` 下全部 10 个底层模型：

- `xgb_anomaly`：1 个 32 帧窗口异常分类模型；
- `xgb_lap_joint`、`xgb_public`、`xgb_public_group`、`xgb_public_sensor_only`：4 个裂纹分类模型；
- `xgb_multiout`：1 个裂纹分类模型 + 4 个几何回归模型。

接口：

- `GET /api/models`：模型清单与文件可用性；
- `POST /api/analysis/process`：运行全部工艺参数模型；
- `POST /api/analysis/anomaly`：运行 32 帧窗口异常模型；
- `POST /api/analysis/all`：同时请求两类分析。

输入缺字段时，模型返回 `unavailable + reason`，不会使用训练范围中点伪造输入。
模型输出保留来源和适用范围；多模型平均值是研究性集成结果，不是机械臂故障概率。

## 4. 数据传输接口

```text
设备/适配器
  → DeviceEvent
  → DataQualityService
  → EventBus
  ├→ REST 最新值/历史值
  ├→ WebSocket /ws/events
  └→ 后续时序数据库、特征仓库和离线训练
```

当前事件总线是有界内存实现，适合联调，不承担长期存储。下一阶段应增加 SQLite/PostgreSQL
元数据与 Parquet/对象存储原始数据，并以焊接任务 ID、设备 ID 和统一时间戳关联四种模态。

## 5. 为什么现在还不能宣称实现预测性维护

现有 XGBoost 模型的标签是“窗口异常、裂纹、焊缝几何”，不是机械臂部件故障、维修事件或剩余寿命。
它们可以作为健康特征，但不能直接推导机械臂何时故障。

达到预测性维护至少还需要：

1. 为每次焊接生成稳定的 `run_id`，完成四模态时间同步；
2. 收集机械臂报警码、轴电流/扭矩、温度、负载、累计运行时间；
3. 接入维修工单、故障时间、部件更换和停机记录作为标签；
4. 建立设备/时间分组切分，避免同一设备或相邻窗口泄漏到训练与测试两侧；
5. 先训练未来 24h/7d 故障概率，再在标签充足时训练 RUL；
6. 采用时间回溯验证，并监控误报率、漏报率、提前量和数据漂移。

`GET /api/maintenance/readiness` 会持续报告四模态数据是否已进入正式管线，并明确维护模型仍缺少什么。

## 6. 启动

```powershell
.\scripts\run.ps1
```

默认不启动 STM32 串口采集。确认真实协议后在 `config/app.toml` 的 `[current]` 中设置
`enabled = true` 和正确串口。`simulated = true` 仅用于联调。
